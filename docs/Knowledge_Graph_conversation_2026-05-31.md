### Project identity (CRITICAL — do not misread)

`codify` is **a CLI tool that uses an LLM to generate context files from a user's project description**. It is **not** a deterministic template engine. The flow is:

```
User description
  ──► Templates (structural guides for the LLM, NOT variable-substitution files)
  ──► LLM API (Anthropic or Gemini)
  ──► Generated context files (AGENTS.md, CONTEXT.md, etc.)
```

It also generates **SDD specs** (`CONSTITUTION.md`, `SPEC.md`, `PLAN.md`, `TASKS.md`) via the `spec` command. As of v3.0.0 it is increasingly positioned as a **workstation/project setup installer + package manager** (marketplace-connected, multi-ecosystem), not merely a "static generator." The strategic framing is **"lifecycle custodian"** rather than "one-shot generator."

## 8. Operational conventions (protocols, gates, restrictions, agreements)

> These are **binding** for the receiving agent. Violating them breaks the maintainer's trust model. Re-read §0's "Hard rules" alongside this.

### 8.1 Commit & VCS conventions

- **No AI credits in commits.** Absolute. No `Co-Authored-By`, no model names, no "Generated with Claude" footer. _(This overrides any default commit-footer behavior.)_
- **Conventional Commits** for every message (`feat:`, `fix:`, `chore:`, `refactor:`, etc.).
- **Protected-branch hook:** direct pushes to `main`/`master` are blocked. **Tag pushes are exempt** (the release workflow needs them). Feature work → `feature/*` → PR → merge.
- **Branch/PR flow** is managed by the `git-workflow-manager` agent (auto-triggers on feature-dev start; invokes `version-manager` after a successful push).

### 8.2 Versioning & release conventions

- **Semantic Versioning 2.0.0.** Bump derived from conventional commits by the `version-manager` agent.
- **`.version` file is the single source of truth.** Currently `3.0.0`.
- **Release = goreleaser-driven.** `.github/workflows/release.yml` fires on tag push, builds darwin/linux × amd64/arm64 tarballs + `checksums.txt`, and publishes a GitHub release.
- **`doc-updater` agent** auto-runs after a new tag to update version references across docs.
- **NEVER cut a release without operator permission.** (See §0 rule 3.)

### 8.3 Quality gates

- **Broken tests are top priority — always.** Maintainer: _"eso debe siempre ser manejado como prioridad."_ Fix them before anything else.
- BDD via Godog. Known suites: SDD standard (18 scenarios), project_repository (14) + workflow_catalog (9) = 23, all green at last record.
- LLM output is validated (`ValidateOutput`) — common gaps: domain entities diluted, naming inconsistency across files, business rules mentioned but not formalized.

### 8.4 Language & terminology

- **Spanish** for comments in domain/context files; **match the maintainer's language** in conversation (he writes Spanish).
- Use **"Track"**, never "Pista", for parallel work streams.

### 8.5 Architecture conventions

- Go with **DDD / Clean Architecture**, **BDD** (Godog), **CLI** with Cobra, **CQRS** in the Application layer.
- Layering: `internal/domain` (entities, services, ports) → `internal/application` (command/query handlers, CQRS) → `internal/infrastructure` (adapters) → `internal/interfaces` (cli, mcp).
- Locale-aware templates: `templates/{locale}/{preset}/`. Presets: `default` (DDD/BDD), `neutral` (generic). Language idioms: `templates/{locale}/languages/{lang}/idioms.template`.
- A **catalog package == one native ecosystem primitive** (1:1 invariant).

### 8.6 ADR convention (IMPORTANT)

- `docs/adr/` is **git-ignored** by project convention. ADRs live **only on the maintainer's local disk**. ADR-0010 (catalog architecture, Track D foundation) and ADR-0011 (SDD pluggable) are local-only. **Cross-check before referencing them as if a teammate can see them.**

### 8.7 Sub-agent automation chain (how work auto-flows)

version-manager       ──(after generating a new tag)──►  doc-updater
